# Build-system foundations for contributed module families

This note connects seven primary sources to the prototype's build architecture, with sources checked on 8 September 2026. It focuses on incremental computation and dependency representation, complementing the [module-system research](RESEARCH.md). The central engineering question is how ordinary Python and small, independently contributed declarations can become independently publishable algorithms without making every contributor maintain the entire dependency graph. The comparisons below are design interpretations, not claims that this prototype implements the surveyed systems or proves their properties.

*Build Systems à la Carte* separates the **scheduler**, which determines execution order, from the **rebuilder**, which determines whether a task needs execution. Its minimality criterion concerns change between builds: tasks execute at most once in a build, and only when they transitively depend on changed inputs. Verifying traces record result and dependency hashes to check whether an existing result remains valid. Constructive traces retain results as well, enabling reuse of a previously computed value, potentially through separate content-addressed storage. Early cutoff stops propagation when recomputing an intermediate value leaves that value unchanged.[^carte2018] This vocabulary gives us several separate implementation goals. A small installed closure measures distribution scope. It does not establish incremental minimality. Stable cell hashes identify reusable implementations, but a persistent trace index would additionally let the builder establish reuse before regenerating their contents.

The current lowering pipeline starts with a root TOML document, contribution fragments and Python source. Static discovery supplies publication roots; authored fragments supply versions and semantic context. Name resolution produces a graph of declarations, including private supporting definitions and referenced assignments. Strongly connected components become shared source cells, then selected roots determine the cells and member facades emitted as wheels. This avoids copying an entire eager package initializer into every algorithm. It also gives shared classes one installed definition, preserving Python identity when several members depend on the same cell.

The expanded 2020 treatment defines build correctness through consistency of reachable derived values with their tasks and final dependencies, while preserving inputs. Its core framework assumes an acyclic task graph and distinguishes dependencies extractable independently of values from dependencies selected using computed values.[^carte2020] For this compiler, contracting declaration SCCs yields an acyclic graph between cells. That is a useful lowering step, not a solution to arbitrary cyclic build tasks. Inside a cell, recursive functions and eager initialization have different ordering requirements. Unsupported initialization and reflection still require diagnostics or explicit adaptation. Build-graph consistency also does not prove that moving a Python definition preserves every observable behavior; original import paths, monkeypatch targets and serialized identities can change.

Shake demonstrates why some dependencies cannot be fixed before a build: a rule can first request a generated file, read its contents, and then request the files named by that result. Its execution model permits dependency discovery during a task, including suspension while prerequisites become available.[^shake] The prototype's similarly named `dynamic_dependencies` field serves a different purpose: it records an author's external package requirements for dynamic Python loading. Neither that declaration nor AST inspection runs candidate code to discover build prerequisites. Treating the two mechanisms as equivalent would hide the need to track generator inputs and generated results.

Buck2's dynamic dependencies provide another useful boundary. A dynamic action can inspect built artifact contents and create subsequent actions; the documentation explicitly presents a restricted mechanism rather than unrestricted dynamic dependency discovery. Examples include dependencies obtained from OCaml analysis and distributed ThinLTO indexing.[^buckdynamic] A future Python generator or native extension adapter could use comparable staging: first produce a dependency description under declared inputs, then lower that description into build actions. This is a proposed extension. The current frontend analyzes existing Python and emits pure Python wheels; it does not schedule arbitrary generated-source stages.

Skyframe makes dependencies part of the evaluation protocol: computations request keyed values through its environment, and unregistered reads can invalidate incremental correctness. Its documented incremental strategy invalidates reverse dependencies of changed inputs, while change pruning preserves downstream results when recomputation produces an unchanged value.[^skyframe] Applying that design here suggests separate cached values for file contents, parsed declarations, resolved bindings, SCC membership, merged contribution metadata and wheel outputs. Directory membership must also be tracked: adding a file matching `members/**/*.toml` changes discovery even when every previously known file remains unchanged. Removing a source binding or changing an import alias must invalidate the affected graph relationships, not merely a final archive.

Those graph caches are not implemented. Each plan and build currently reparses and analyzes the package and regenerates selected wheel bytes. Byte-identical existing wheels are retained without changing their modification times. This verifies an output match after computation; it does not skip that computation. Unsupported source elsewhere in the package can still block a selected build. The next incremental experiment should separately measure source discovery, parsing, name resolution, SCC maintenance, metadata merging and emission, with cold builds, unchanged builds, unrelated edits and shared-dependency edits. Reporting only selected wheel count would conceal analysis costs that grow with the family.

Buck2's transitive sets address a related representation problem: dependency information can share recursive structure, with projections that defer expansion instead of repeatedly flattening every transitive collection.[^transitivesets] The design implication for thousands of algorithms is to store direct relationships and shared cells, then expand a closure for a selected operation when needed. Independent publication need not entail an independently copied implementation tree or a complete repeated dependency inventory. The prototype already shares implementation cells and accepts contributor fragments through globs. It has no persistent transitive-set store, and its whole-package in-memory analysis remains a scalability boundary. Contributor count, graph size, shared-dependency density and closure size are distinct workloads.

Bazel's hermeticity guidance ties repeatability to isolation from undeclared host inputs and to treating tools and dependencies as controlled inputs.[^hermeticity] Fixed ZIP timestamps, stable ordering and content hashes therefore establish a narrower property here: repeated builds in the tested environment can produce identical artifact bytes. The prototype does not pin the Python toolchain, compression implementation or complete external dependency environment. A member lock covers internal artifacts, not a solved third-party environment. Metadata and license changes can alter wheel bytes independently of executable statements; license bytes currently are not folded into cell names. Hash verification detects byte differences, but it does not establish complete provenance, behavioral equivalence or reproducibility across environments.

Adaptation agents fit at an explicit authoring boundary. They can propose a wrapper, replace unsupported reflection with explicit bindings, annotate a problem domain, declare a required interface, or add focused validation. The resulting Python and local TOML should be reviewable build inputs. Source edges answer which definitions an implementation references; semantic requirements answer which interchangeable module must be supplied; descriptions of intended problems support discovery. None can substitute for the others. An agent's claim that two processors satisfy the same interface remains a claim until the relevant structural and behavioral obligations are checked.

For an adaptation experiment, record the original source revision, proposed changes, declared contracts, observed failures and validation results. If agent execution later becomes an automated build stage, its inputs and produced artifacts must be captured explicitly; a model invocation is not automatically deterministic because its output is subsequently hashed. The immediate research program is consequently testable: evaluate contributor-local declarations, closure isolation, incremental invalidation and adaptation success separately. These sources justify concrete architectural directions and sharper measurements. They do not establish that the present prototype supports arbitrary Python, proves semantic substitutability or sustains an internet-scale repository.
